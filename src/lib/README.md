# `src/lib`: where everything lives

Pages are in `src/routes` (one folder per URL). Everything they use is here,
grouped by feature. Import from here with `$lib/...`.

| `arranger/`       | The rhythm-section arranger (the `/arranger` page): chord charts, instruments, playback, melody. See [arranger/README.md](arranger/README.md).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `sampler/`        | The sampling page (`/sampler`, a dev tool: local dev on a computer only): record your own instrument samples: the input check and test take, then a guided session (checklists and a what-to-record list, take analysis and checks, many hits per recording to choose from, progress, export as WAVs + manifest, and a copy of every kept take in `samples-source/`).                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `audio/`          | The sound engine, shared by every page and knowing nothing about songs: AudioWorklet DSP (`worklets/`, the one place they're loaded), EQ, reverb and the output stage (loudness, true-peak limiter) as building blocks, the mixer's audio graph and fader curve (`mixer/`), meters and the shared frame loop (`analysis/`), recording from a microphone or interface (`recording/`: the input, the recorder, take playback, a click track; used by the sampler and by recording along) the time stretcher (`stretch/`: plain DSP, run by the `stretch-player` worklet and by Node tests) and the tuner's DSP (`tuner/`: McLeod note finding, a phase lock-in for the cents, run by the `tuner` worklet), and `players.js`: each page's players sign up with a pause, so the tuner can pause whatever is playing. |

## A few conventions

- **Small pieces, composed.** Functions live in their own modules and are imported by thin components. Each decision (a limit, a list of choices, a colour) lives in one place, so a change of direction is a one-file edit.

- **Files ending `.svelte.js`** use Svelte's reactive state (`$state`,
  `$effect`) outside a component. The suffix is required for that.
- **Styling** comes from the tokens in `theme/tokens.css` and the classes in
  `theme/ui.css`. Components don't use raw colours, so changing the look (or
  a user's Appearance settings) restyles everything.
- **Saving data** always goes through `storage/` (or `settings/` for
  preferences), never straight to `localStorage`, so where data lives can
  change in one place.

## How the code is layered

Three layers, and imports only point down:

1. **Song logic** (plain `.js`: `arranger/chart/`, `theory/`, `bass/`, `instruments/`,
   `melody/`, `transcription/`, `tracks/`, `export/midi.js`, and `audio/`): plain
   functions of their inputs. They never read the open song or app settings
   (`.svelte.js` state); whatever they need is a parameter. That's what makes
   them testable on their own (see Tests below).
2. **State** (`*.svelte.js`: `arranger/state/`, `arranger/mixer/`,
   `TranscriptionState`…): what the page knows, and the edges that read it and
   pass it down (e.g. `bassSongOf()` handing the chart, key and capo to the bass logic). The open
   song's texts are parsed here, once per change (`ArrangementState`,
   `MelodyState`, `BassState`), and handed down already read.
3. **Components** (`.svelte`): thin; they show state and call its methods.

A few plain modules sit at the edge on purpose and read app state: recording
along (`takes/recordAlong.js`), gathering and receiving a shared song
(`share/gatherSong.js`, `share/receiveSong.js`) and the download helpers
(`export/exportAudio.js`, `export/downloadMidi.js`).

## Tests (not set up yet)

Everything in layer 1 can be tested in Node without a browser. When tests are
added, Vitest is the natural choice (it runs through the project's Vite
config, so `$lib` paths and JSON imports work as they do in the app). Until
then, check logic with a throwaway Node script; only `guitar-chords.json`
(imported by `instruments/chordBook.js`) needs stubbing there.

## A backend later

Everything saved goes through `storage/`. Songs (`storage/arrangements.js`)
are read and written with async functions already, so when they move to a
server (SvelteKit server routes, or an API of its own) only that module's
bodies change. The other collections (`storage/collection.js`: EQ presets,
listening setups, chord shapes) are still synchronous; they'd follow the same
way. Takes are in IndexedDB (`storage/songTakes.js`, async). Paid features
check `account/plans.js`, and the server must check the same list.
