# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev`: Vite dev server.
- `npm run build`: production build. Use it as the type/compile check.
- `npm run lint`: runs `prettier --check` and then `eslint`.
- `npx eslint <files>`: lint only the files you touched.
- `npm run format`: prettier write.

There is no test runner yet (Vitest is the planned one: it reads the Vite config, so `$lib` and JSON imports just work). To check pure logic (bass lines, event timing, MIDI bytes), run a throwaway Node script in a scratch directory; only `guitar-chords.json` needs stubbing, because song logic never imports Svelte state (see "Layers" below).

## Stack

- SvelteKit with Svelte 5 runes (`$state`, `$derived`, `$effect`), plain JavaScript with JSDoc types (no TypeScript), Tailwind v4, Tone.js.
- **Prefer the Web Audio API itself** wherever it's the better tool: native nodes (`BiquadFilterNode`, `IIRFilterNode`, `ConvolverNode`, `AnalyserNode`, `GainNode`…) and `AudioWorklet` for custom DSP. The user wants to use Web Audio's full capabilities, and more DSP is coming. Tone.js stays for scheduling, samplers and the existing channels; new processing goes in native nodes or worklets.
- The `.svelte.js` suffix is required for any module that uses runes outside a component, e.g. `mixer.svelte.js`.

## The song is read once

A song is three texts, and each is parsed in one place, once per change, as a `$derived` in state. Everything else takes what it needs from there; nothing parses the open song's text itself.

- **The chart** (`arrangement`): `ArrangementState` (`readArrangement`) → `arrangement.sections` and the rest.
- **The tune** (`abc`): `MelodyState` (`melody/readTune.js`, abcjs `parseOnly`) → `melody.tune` (abcjs's parse), `melody.sequence` (as played, for chord symbols), `melody.line` and `pickup` (the band's notes), `melody.voices` (a score per voice for the piano roll, worked out only when something asks), `warnings`, `title`.
- **The bass** (`bass`): `BassState` → `bass.read` (its score) and `bass.written` (the notes the band plays, null for the band's own line).

abcjs loads after the page: `state/abcjsLoaded.svelte.js` holds it, the reads are empty until it arrives and redo themselves when it does. Code that must have the tune right now (Play, Export, writing harmony) does `await abcjsReady()` first. Plain logic takes abcjs or a parsed tune as a parameter (`tuneReader(abcjs)` for code that reads _other_ versions of a text: the band's own bass line, a harmony option, the steps of one roll edit).

**Drawing is only the sheet music's job** (`components/melody/SheetMusic.svelte`, `melody/drawSheetMusic.js`): abcjs can only draw from text, so `renderAbc` parses again there, and only while the sheet music is on screen. It gives back just the drawn notes' positions for the cursor. A pickup is drawn ending with a double bar line, and its notes are drawn again in the last bar's closing beats where that bar only rests (the tune goes round) (`pickupsOnPaper` in `melody/roll/pickupBar.js`, in `SheetMusic.svelte`: only on the page, the saved ABC keeps its plain bar line and rests). Measured in the browser: one `parseOnly` per keystroke in the ABC box (about 1 ms on Amazing Grace), per roll edit, per harmony option tried; a chart change parses only the band's fresh bass line when the bass is edited. Still parsing for themselves, on purpose: `transposeAbc` (a capo move; abcjs's transposer wants its own parse) and one melody edit in the roll, which parses each in-between version once (words, then harmony).

## Layout

Code is grouped by feature under `src/lib/`. `src/lib/README.md` and `src/lib/arranger/README.md` are the maps; keep them current when adding or moving files.

**Layers** (the rule that keeps logic testable; `src/lib/README.md` has the detail): song logic is plain `.js` and never imports `.svelte.js` state: whatever it needs (the bass style, the mix) is a parameter, and state or a component at the edge passes it (`chosenBassStyle()`). `.svelte.js` state sits above it, thin components above that. The sound engine that knows nothing about songs is `$lib/audio/` (worklets, EQ, reverb, output stage, meters and frame loop, the mixer's graph builder and fader curve, mic recording, the time stretcher); the band's mixer state is `arranger/mixer/`. **A backend** is coming (SvelteKit server routes or an API): song storage is async already (`storage/arrangements.js`), so it's the one module that changes; keep new saved data behind `storage/` with async functions. **Paid plans**: `$lib/account/plans.js` is the one place that says what each plan includes; code asks `planAllows('feature')`, never a plan's name (first entry: lossless take sharing).

## Arranger architecture

### Arrangement text

Parsed by `parseArrangement.js`. Example: `"Chorus"|G,G|C,C|G,G|D,D|`, plus `"Break" as Chorus` for repeats.

- Each line is a section.
- `|` separates measures and `,` separates chords within a measure. A bar's beats are split evenly between its chords, with any odd beat going to the earlier chords. An empty bar (`|G| |`, or `||`) keeps the chord before it, as in written music (not a stop: that's N.C.); `chart/chartTokens.js` is the one rule for what counts as a bar, shared by the parser and the writers that find a bar in the text (`withBarChords`, `analysisMarks`). The parser keeps which bars were empty (`held`, parallel to `measures`, carried through `as` and loop regions); `chartBars.js` marks them (never the first bar) and every view draws them without a chord name: the strip, the help examples, Transcribe's chord lane (an empty chip; `barChords.js` `isHeld`: slots with no chord, while an N.C. bar has none stored; opening and leaving one keeps it held, clearing a written bar makes it N.C.; `chartFromBars` writes it back empty), and the Band/Tracks chord blocks (one block stretched over it).
- `N.C.` (no chord) is a stop: the band rests there (`|G,N.C.|` for half a bar). It names no key. `chart/noChord.js` is the one place the band learns it: `sectionsToPlay` fills each N.C. with the chord before so instruments can work out their parts, then `withoutStops` drops notes starting in one and `endBeforeStops` cuts ringing guitar notes (used by `instruments/performance.js`, `export/midi.js`, and `bass/songBass.js` `bandsBassLine` for the band's own bass; an edited bass plays as written). `guessedKey` skips it; harmony and the roll's chord dots get no chord there; a blank tune writes no chord symbol for it.
- `[K:G]` names the song's key when the first chord doesn't (see "The song's key" above).
- **A chord the band can't play is pointed out as it's typed** (`chart/knownChords.js`, the one check: N.C. or a name the chord book has a shape for, built in or My chords): the chart editor's red line names it and its bar, Play says the same (`arrangement.error`; `readError` is only an unreadable chart, which is what stops Transcribe writing), Transcribe refuses it in the chord boxes (the bar stays open, the box framed, the message under it) and draws a chart's unknown chord as a red chip.
- `A7{V7/V}`: your own analysis of a chord, for the Roman display; the band ignores it (`chart/analysisMarks.js`).
- Time signatures use abc-style inline fields:
  - `[M:3/4]` lasts until changed, carrying into later sections.
  - `[2/4]` applies to one bar only (crooked tunes).
  - The default is 4/4.
  - Only denominators 4 and 2 are supported.
- Sections store `measures: string[][]` plus a parallel `meters`.
- **When the syntax changes, update the help page** `src/routes/arranger/help/+page.svelte`.
  - Its audience is non-technical, so keep it in plain language with one idea per section.
  - Each example goes through `{@render example(...)}`, which draws it as a chart. The examples must parse.

### `timeline.js`

The single source of musical time. All times are in quarter notes.

- `slotPositions` gives each chord's start and length.
- `rhythm` gives the boom/chuck grid: `beatGroups` makes 2 = boom-chuck and 3 = boom-chuck-chuck.
- The guitar, mandolin, bass line, MIDI, chart and playhead all derive from it. Never assume a fixed bar length.

### `guitar.js`

The core of the arranger.

- **Chord shapes** come from `guitar-chords.json`. Each shape is 6 frets from low E to high e, with `null` for a muted string. The capo adds to every fret.
- **The chord book** (`instruments/chordBook.js`) is the one place a chord name becomes a shape: `chordShape`/`hasShape`, used by `guitar.js`, the capo choice in `abcChords.js` and the help page. It looks in your own shapes first, then `guitar-chords.json`. Voicings built from theory should plug in here.
- **My chords** (`voicings/`, UI `components/voicings/`, button beside the editor's ?): your own shapes, typed as frets (`3,x,0,0,3,3` or `3x0033`), saved on this device for every song (`storage/chordVoicings.js`, a `collection.js` document: `name`, `frets`). `myChords.svelte.js` loads them on page start and hands them to the chord book (`useYourShapes`), so playback, export and MIDI all use them. A name can be a new chord (`Cadd9`), a variant (`G:high`: the part before the colon says what the chord is; `withoutVariant` drops it, e.g. when writing chords into ABC), or a built-in name, which then replaces the built-in shape. `checkVoicing.js` refuses a shape without a root and fifth for the boom or without a strum string. The form keeps a draft (`ChordForm.svelte.js`). On a phone, the keypad's Mine key types your chord names. A song using one of your shapes won't play on a device that doesn't have it (the error says so).
- `guitar-chords.json` has major, minor, 7 and dim in every key (both sharp and flat names), lowest position, open strings where they fit. **Slash chords** (`G/B`) strum the chord's shape and boom the slash note, the lowest one on the bottom three strings up to fret 4; the alternating boom is the chord's fifth, or its root when the fifth is already the bass (`alternatingPitchClass`). The MIDI bass follows the same rule. abcjs writes chord flats as ♭; `plainChordName` in `abcChords.js` turns them back.
- **Samples** are in `static/samples/guitar/{E,A,D,G,B,ee}{0..12}.mp3`.
- **`buildEvents`** turns sections into timed note events:
  - Each beat group of the rhythm grid gets a **strum pattern** (`strumPatterns.js`, plain data): one character per stroke of a hand that keeps moving down and up (even = down, odd = up), `B` bass, `x` strum, `.` miss, at `steps` strokes per quarter. Boom-chuck and bum-titty (`B.xx`: a quarter, then two eighths down-up; in 3/4 `B.x.xx`) mixed at random, half and half for now (`STRUM_MIX`, seeded so export and MIDI match live's first pass). A new pattern is one entry.
  - Root and fifth alternate on the `B`s within a run of the same chord; both are found as the lowest note in the shape with the right pitch class.
  - A strum is strings 3–5; an upstroke plays them high to low, 3 dB lighter. A light upstroke graze (top two strings) sounded wrong with these samples: it cut the chuck's ring short and replaced it quieter. Try again with real graze samples.
  - A string sounds one note at a time: striking it again damps the old note, which fades in 15 ms from the moment the new one starts (`RESTRIKE_FADE`). A chord change fades it in 50 ms (`CHORD_CHANGE_FADE`). Looping, the guitar's notes span 4 passes (`LOOP_PASSES`), so the sprinkle varies.
- **Strum spread** uses a pendulum model of the right hand (string spacing and swing amplitude vs. tempo; faster strokes swing smaller). Hypothesis to test: bluegrass is more a bounce (the hand speeds up and slows down through the stroke) than a pendulum; Irish keeps the pendulum.
- Tried and dropped (too subtle to hear, or not wanted): a fake round robin (nudging each sample's pitch, level and start; real round robins come with the recorded samples) and a hand feel (one random force per stroke setting level, brightness, sweep speed and timing).
- **Pluck and graze** (`instruments/articulation.js`, plain data, the user's ear): a single note is plucked (the pick grabs the string), every strummed note grazes (it brushes past), whatever the tempo; a strum never has a pluck's attack. Booms pluck, the guitar's strums graze, and so do the tune's stacks and the mandolin's chops (`mandolin.js` `CHOP_ARTICULATION`: the chop samples alone sounded harsh; the mandolin channel gets the graze's low-pass, `band.js`). Faked from the plucked samples until graze samples are recorded (then a graze picks those, in that one place): 4 dB quieter, a 5 kHz low-pass, the pick's click skipped (the sample starts 6 ms past where its sound begins, `soundStart.js`, measured once per sample in the browser: Chrome decodes about 11 ms of MP3 silence before the pick, ffmpeg 23 ms; the note still lands on time) and a 4 ms fade-in. The user likes the guitar's; the mandolin's chops still sound off, probably the samples. The boom and strum faders on the guitar's strip were removed once the graze did their job: the balance between boom and strum is the articulation's, not the mix's (an old mix's levels for them are ignored; MIDI velocities follow the articulation). Ideas not built: shaping only the first 10–20 ms (transient), a thinner body (a little low-mid cut).
- **Lighter touch** above 120 BPM, on top of the articulation: lower level, low-pass filter and softer attack (`touch` in `guitar.js`).
- **`playArrangement`** (now in `playback/livePlayback.js`) places every note at an absolute audio-clock time (`start + pass × duration + offset`).
  - A Tone context timer queues passes within a lookahead, catches up if it's late, and skips past-due notes.
  - Don't use `setTimeout` for musical timing.
  - It returns `{ position(), stop() }`.

### The mixer (`mixer/`, its engine in `$lib/audio/`, UI in `components/mixer/`)

- `mixer.svelte.js` holds the settings, with snapshot, apply and reset. `faderTaper.js` holds the fader curve. `mixerGraph.svelte.js` builds the Tone graph lazily and keeps it in step.
- Each instrument has a channel (input trim → EQ → fader/pan), a post-fader send to the reverb aux, mute and solo.
- Instruments connect via `getChannel(id)` from `mixerGraph.svelte.js`.
- Meters and the master visualiser read **analyser taps** (`$lib/audio/analysis/taps.js`), created in `mixerGraph.svelte.js` and published as `audioTaps.current` (null until the first Play).
  - There's one tap after each channel's fader and pan, one on the reverb aux, the master's waveform and spectrum (taken after the output stage: what reaches the speakers), and the output stage's loudness/limiter readings.
  - A tap always exposes its data through a function (`read()`). `audioTaps` is `$state`, and Svelte's proxy copies a plain object's values the first time they're read, so an object that audio code keeps mutating would freeze in the UI.
  - Everything that animates subscribes to the one shared loop in `$lib/audio/analysis/frameLoop.js` (`onEveryFrame`), and writes straight to the DOM or canvas each frame, not through Svelte state.
  - Level maths is in `analysis/levels.js`; meter movement (fall, peak hold, clip latch) is in `analysis/meterBallistics.js`.
  - The meters use the fader's dB scale, so they line up with its marks.
  - The master visualiser is a small fixed-size card after the master strip (size: `--scope-width` and `--scope-screen-height` in `MasterScope.svelte`). Its views are separate draw functions in `components/mixer/scope/`.
- The automated browser pane in this app doesn't run `requestAnimationFrame`. To test meters or the visualiser there, replace it with a 16 ms timer, then navigate away and back so the frame loop restarts on it.
- The default mix (pans, sends, reverb level) is a documented block at the top of `mixer.svelte.js`. Resetting a control (tap its readout, double-click its cap) returns it to that default.
- **Headroom.** Every channel starts with an input trim (`INPUT_TRIM_DB` in `mixerGraph.svelte.js`, −14 dB), before its EQ. With every fader at unity the master peaks around −8 dBFS: healthy mixing headroom. Change the trim, not the samples or instrument levels, to move the whole mix up or down; it keeps the balance between instruments. Loudness is added at the very end, by the output stage, never by raising the trim.
- **Output stage** (`$lib/audio/output/`, after the master fader; the "Loudness" strip, `components/mixer/output/`). Like a mastering chain: output gain (native `GainNode`) → true-peak lookahead limiter (worklet) → compare trim → speakers, with a loudness meter branch (K-weighting as two native `IIRFilterNode`s → worklet).
  - The user never wants the master to clip and doesn't want loudness left on the table. Target −14 LUFS (streaming level), ceiling −1 dBTP; tuning constants in `output/outputSettings.js`. `DEFAULT_OUTPUT_GAIN_DB` (+7.7) was measured in the browser: the starter song's default mix is about −21.7 LUFS before it.
  - `mixer.output.gain` saves with the song. Match (`mixer/outputStage.svelte.js`) sets it from the song's integrated LUFS since Play; the integrated reading resets on Play and on a gain change.
  - Compare is a level-matched A/B (not saved): while comparing, everything is trimmed back down by the output gain, and B bypasses the limiter, so A and B differ only by the limiter.
  - Verified in Node against references: K-weighting matches the BS.1770 48 kHz table; a −20 dBFS stereo 1 kHz sine reads −20.0 LUFS; the limiter holds plucks, clicks, +12 dB sines and inter-sample test signals to −1.0 dBTP, and passes signals under the ceiling bit-exact (5 ms delay). Its detector uses 16 taps per phase (12 let full-band noise through by ~1 dB).
- **AudioWorklets** (`$lib/audio/worklets/`): our own DSP on the audio thread. `worklets.js` is the one place they're loaded (Tone's loader only takes one module per context); a new processor is a self-contained `*Processor.js` file (no imports) plus one line in `PROCESSORS`. ESLint gives `**/worklets/*Processor.js` the worklet globals, and `vite.config.js` keeps processor files from being inlined as data: URLs (Safari won't load those). A processor that throws logs `Audio processor "…" stopped`. In the browser pane, a worklet's messages arrive normally; for its numbers on screen, use the rAF-timer trick above.
- **EQ** (Logic Channel EQ-style) on every channel, the reverb aux (after the plugin) and the master (the whole mix):
  - Bands and their defaults are defined once in `$lib/audio/eq/eqBands.js`: low/high cut (12 or 24 dB/oct), low/high shelf, four bells. The settings live in each strip's `eq` in `mixer.svelte.js` and save with the song.
  - `createEq.js` builds it from native `BiquadFilterNode`s, because `Tone.Filter` rejects the negative Q a Butterworth cut needs in dB. A 24 dB/oct cut is two 12 dB stages.
  - `eqResponse.js` works out the curve with the same (RBJ) formulas the browser uses, for the graph and the strip thumbnails; it matches `getFrequencyResponse` exactly.
  - The UI is `components/mixer/eq/`: `EqButton` (the curve thumbnail, under the name at the top of every strip, placed by `Strip.svelte`) opens one shared, non-modal `EqWindow` (`eqWindowState.svelte.js` says which strip). The graph shows the strip's sound after the EQ (`audioTaps.current.afterEq`).
- **Listening setups and EQ presets.** Every speaker and pair of headphones sounds different, so the user should tune and save EQs per device and per speaker/headphones; the UI says so plainly, so keep that wording when changing it.
  - A listening setup is every strip's EQ (`eqsSnapshot`/`applyEqs` in `mixer.svelte.js`, strips from `stripsWithEq`). `mixer/listeningSetup.svelte.js` is the one place for its rules: this device's setup goes on at page start and stays through New and Open (`applySongMix`); while it's in use the song's own EQs are put aside and saved back unchanged (`songMixSnapshot`), so it never marks the song changed; setup edits save themselves (`state/autosave.svelte.js`; switching setups saves the one in use first).
  - The UI is `components/mixer/listening/`: a small button in the mixer's title row (kept small so the drawer fits a phone) opens the "What are you listening on?" dialog. The EQ window's note links to it.
  - EQ presets (`mixer/eqPresets.svelte.js`, UI `eq/EqPresetPicker.svelte`) are one strip's EQ; any preset loads on any strip, the strip's own listed first.
- **Every bus after the channels must be stereo** (`new Tone.Channel({ channelCount: 2 })`). A Tone Channel defaults to mono and would fold every pan back to centre; that was the "pan does nothing" bug.
- Solo is done in our own code, not Tone's `Channel.solo`, which would also mute the master and aux. A soloed channel mutes the others; the reverb aux is solo-safe. Solo isn't saved with a song.
- The reverb aux is Logic-style, a strip with an insert slot (power = bypass) that opens the plugin window, a non-modal `Dialog`.
  - The plugin is hand-built on Web Audio (`$lib/audio/reverb/`): a generated impulse response (decay, damping, width) into a convolver, plus pre-delay, low/high cut and separate wet/dry (100/0 by default).
  - Its controls are defined once in `reverbSettings.js`.
  - Older songs' `reverb.decay` maps to `plugin.decay` in `applyMix`.
- New instruments should add a channel to `mixer.channels` rather than connect to the destination directly.
- Every mixer control is a `Slider.svelte`, the same on desktop and touch. Only the cap drags, and it moves relative to where it is, so the track never jumps. Off the cap, touches are left to the page (`touch-action: pan-x`). Tapping the readout resets; arrow keys step past detents.
- The console is one row that scrolls sideways on narrow screens, so in the mixer up/down only ever means a fader. Keep strips short enough that the drawer fits a phone without vertical scrolling, upright and on its side.
  - On its side (`max-height: 600px`, the one breakpoint for it), each strip lays its controls out two to a row beside the fader (the fader is always a strip's last control), name beside EQ; the drawer goes up to the top bar, the player bar slims down, and the hint line hides. Measured at 812×375: the drawer fits exactly above the player bar.
  - Slider tracks use `touch-action: pan-x pan-y`: the console's own `pan-x` still limits the mixer to sideways swipes, while a window like the EQ can scroll up/down over its sliders.
  - Floating windows start just under the top bar on short screens, and the EQ graph is shorter there (9rem), so the EQ window fits a phone.
  - `:hover` styles go inside `@media (hover: hover)`: on a touch screen a tapped hover sticks.

### Playback and export: one band, two clocks

- `instruments/performance.js` (`preparePerformance`): every note of every instrument for a song, as plain data (loop for live; one pass for export, like the MIDI file).
- `instruments/band.js` (`createBand`): turns a performance into sound (sample players, the upright synth, touch filters) in the current Tone context. `{ live: false }` for offline: Tone reports an offline player stopped before it has played, so the live clean-up (dispose on stop) would silence it.
- `playback/livePlayback.js` (`playArrangement`): the lookahead scheduler. `$lib/audio/mixer/buildMixerGraph.js`: the whole mixer in any context; `mixerGraph.svelte.js` is the live wrapper.
- **Export** (`export/`, the Export… button and dialog in `components/export/`, phone and desktop; MIDI is a choice there, hidden on touch):
  - `renderSong.js`: `Tone.Offline` at 48 kHz renders one pass + a reverb tail (decay + 1 s, 2–8 s). Bar 1 starts one bar in when the melody has a pickup, so files line up with the `.mid`. Full mix = as heard (mutes kept, solos dropped). Stems come from one render, each to its own channels of a native `ChannelMergerNode`: dry by default (after the input trim: mono, unity, no EQ/pan/reverb) or processed (post-fader stereo + a Reverb stem; they sum to the mix before the master). Stems ignore mutes.
  - Don't set an offline destination's `channelCount` (it's fixed; setting it throws a message-less `InvalidStateError`); only `channelInterpretation: 'discrete'`.
  - `wav.js` (24-bit PCM) and `zip.js` (stored, CRC-32) are hand-written and checked against Python's `wave` and `zipfile`. `exportAudio.js` names (`song-120bpm.wav`, `song-120bpm-stems.zip`) and downloads.
  - Rendering stops live playback first (Tone.Offline swaps Tone's global context).
  - Measured on the starter song: full mix 2.5 s to render, peak −1.0 dBFS; stems + mix 8.5 s; melody pickup at 1.0 s, bar 1 at 1.5 s, 29.0 s long.
  - Later: compressed formats for sharing (WebCodecs `AudioEncoder` can make AAC/Opus without a library like ffmpeg.wasm).

### `midi.js`

- A hand-written Standard MIDI File (format 1, PPQ 480), not `@tonejs/midi`.
- It contains a tempo track with markers per section, the guitar track (channel 1), a separate bass track (channel 2), the mandolin chop (channel 3) and, when there's an ABC melody, a Melody track (channel 4, same guitar-sampler mapping, one pass with no trailing pickup).
- If the melody has a pickup, every track moves one bar later so the pickup can end that bar; the arrangement then starts on Logic's bar 2.
- Track names match the user's Logic instruments ("Bluegrass Guitar" sampler preset, "Roots Upright").

**Note numbering.** Logic numbers middle C as C3.

- The guitar is shifted by `GUITAR_OFFSET = 12`, so the low E sample sits on Logic's E2.
- Bass pitches in `bassline.js` are already in file numbering (range 40–55).

### `melody.js`

- An optional melody in ABC notation (the "Melody" box on `/arranger`), drawn with abcjs and played through the `melody` mixer channel. abcjs's own playback is not used.
- **What the tune plays on** is picked per tune channel (Melody and every harmony part): a button on its strip (`components/mixer/instruments/InstrumentButton.svelte`) opens one shared modal, `InstrumentWindow.svelte` (`instrumentWindowState.svelte.js` says which channel), listing every instrument by family; tapping one picks it and, while stopped, plays a note on it (`auditionNote` takes a channel; piano-roll notes audition on the edited voice's). The channel's `instrument` saves with the mix; the defaults give each part its own (`TUNE_INSTRUMENT_DEFAULTS` in `mixer.svelte.js`: melody electric piano, so the tune sounds at concert pitch as written (the guitar samples sound it an octave lower, as guitar music does), tenor fiddle, high baritone flute, baritone clarinet, low tenor cello). The list is data in `instruments/tuneInstruments.js`: the guitar samples plus about twenty Tone.js synth recipes standing in until there are samples (voice, options, vibrato, octave, a measured level); a new instrument is one entry. `band.js` asks for each note's instrument as it plays it, so a change is heard while playing; export reads the mix's. MIDI export is unchanged. Planned: controls over each sound's shape (attack, brightness, vibrato), a section of the same window writing per-channel overrides onto the recipe.
- `melodyFromTune` takes a parsed abcjs tune. It uses `tune.setUpAudio` (repeats and endings played out) to get notes in quarter notes, timed from bar 1's downbeat, so pickup notes are negative. It finds the pickup itself, because abcjs's `getPickupLength` misses a pickup written after `|:`.
- Sync contract: the melody and the arrangement are written separately and only share a clock. The melody's bar 1 starts with the arrangement's bar 1, at the arranger's tempo (the ABC's `Q:` is ignored). The melody loops with the arrangement's pass length. Anything past the end is cut, and a short melody leaves a gap.
- The pickup plays before the band (`leadIn` delays the band's start) and again at the end of every pass.
- A loop region plays the matching melody bars (`loopOffset` in `loop.js`).
- Pitch: ABC is concert pitch, so a note sounds at written MIDI −12 (guitar sounds an octave below written) + transpose (the Key setting). The capo doesn't move it: the arrangement's shapes + capo reach the tune's concert key.
- Moving the capo asks whenever the chart has chords, melody or not (`components/player/CapoChoiceDialog.svelte`, logic in `Arranger.setCapo`): raise the song (the ABC, if any, is rewritten by `melody/transposeAbc.js`, abcjs `strTranspose`) or keep its key (the chart's chords move to new shapes, `chart/transposeChart.js`). Either way the ABC stays at concert pitch, so nothing in the saved shape changed.
- The sheet music has two views once there's a capo or key change (`SheetViewToggle.svelte`): Concert (as it sounds, the Key menu included) and Guitar shapes (the chart's key, to read with the capo on). Display only, via abcjs `visualTranspose`; that also moves chord symbols, so `drawSheetMusic` reads the chord sequence from an untransposed parse. `finger()` picks strings with a position-playing hand model. Notes above the high-e 12th fret sample are resampled.

### `abcChords.js`

- Converts chords both ways between the ABC melody and the arrangement. Both directions read `abcjs.synth.sequence(tune)`, which lists the tune in play order with repeats and endings played out. Each note or rest has `timing` (its place in the written score, in whole notes), `duration`, `chord`, and `elem.startChar`.
- `arrangementFromAbc`:
  - Bars come from the bar lines. A pickup is dropped. A short bar at the end of a repeat is merged with the pickup that follows it.
  - Chords change on the nearest beat, using the fewest even slots (`G,C,D` = 2+1+1).
  - Sections split where the score jumps back (a repeat). They're lettered A, B… by where they start in the score, and an identical repeat becomes `"A" as A`.
  - The capo is chosen so chords land on shapes in `guitar-chords.json`, preferring G/C/D/Am/Em home shapes.
- `abcWithChords`: writes the arrangement's concert-pitch chords into ABC that has none, on the note where each change lands. It reports changes during held notes, and repeated bars the arrangement chords differently on another pass.
- Chord shapes are bluegrass voicings with a low fifth, so `bassNote` can alternate root and fifth. Keep that when adding shapes.

### Harmony parts (`melody/harmony/`)

- Up to four parts (`harmonyParts.js`, data: tenor, high baritone, baritone, low tenor), each counting chord tones from the lead (+1 = next chord tone up). The toggles are `components/melody/HarmonyParts.svelte`; `Arranger.writeHarmonies` writes them.
- `harmonyNote.js`: on a chord tone (root/3rd/5th of the band's concert chord, `chart/concertChords.js`), count along the triad; on any other note, along a close triad built on the melody note from the chord's scale (`theory/chordScales.js`), so parts move in parallel. Sixths come out of this naturally (high baritone over the 3rd).
- `writeHarmonies.js`: each part is the melody's own ABC text with pitches swapped (rhythm, ties, repeats kept; chord symbols, grace notes and lyrics dropped), appended as `V:<id> name="…"` after the melody, which gets a `V:1` line (abcjs plays voices together only then). Rewriting replaces the parts; removing all of them gives back the original ABC. Spelling and accidentals through `abcPitch.js` (`musicInKey.js`). Single-voice melodies only. Repeated bars take the first pass's chord.
- Each part has its own mixer channel (id = part id, added to `mixer.channels` from `HARMONY_PARTS`, saved with the mix like any strip). `partChannels.js` is the one place that maps voices to channels: abcjs keeps only a voice's name (`staff.title`), so a voice named like a part plays on that part's channel, anything else on Melody. Every `MelodyNote`/`MelodyEvent` carries its `channel`; `band.js` connects by it, stems include a part's channel only when the song has it, and the MIDI file gets one track per voice (channels 4–8). The mixer shows a part's strip only while the song has it; removing a part clears its solo. The pickup is read from the first voice only.
- Ideas not built: a passing note held against a chord tone (oblique motion) instead of parallel; parts above the lead drawn above it (`%%score`); counterpoint.

### `follow.js`

- While playing, the sheet music follows the band: the sounding note gets the `abcjs-playing` class, an `abcjs-cursor` rect glides across the staff, and the page scrolls to a new line if it's out of view (only while the sheet music is on screen).
- Positions come from abcjs `TimingCallbacks(tune).noteTimings`, which lists notes as played (repeats expanded) with their SVG `elements`, `left`, `endX`, `top` and `height`. Its milliseconds are rescaled to quarter notes by proportion (total played quarters ÷ total ms), because abcjs's `qpm` counts the meter's beat, not quarters.
- Time comes from `playArrangement`'s `beats()` (the audio clock), mapped the same way `melody.js` times the melody (`melodyTime`), never from abcjs's own timer.

### `bassline.js`

- The MIDI-only bass part: root–fifth (usually the fifth below) and stepwise walks/approaches into chord changes.
- **How busy it is is a style** (`instruments/bassStyles.js`, plain data: `leadInChance`, `fillUnderTune`; a new style is one entry, a new knob one field read in `bassline.js`). **It's part of the song** (`bassStyle`, song version 3: saved, drafted and shared with it), picked under the piano roll while editing the bass (`BassLineNote.svelte`), default Root and fifth (no walks, no fills, repeats play the same); Active is the walks and fills below. `bass/songBassStyle.svelte.js` holds the open song's and is the one place both writers of the band's own line read it (`bassPart`, `generatedBassAbc`); the roll redraws when it changes; an edited line ignores it. A change is heard on the next Play.
- Choices are seeded (mulberry32), so exports are deterministic.
- Repeated sections (same chords) are guaranteed to differ from their previous pass.
- With a tune, wherever the lead holds a note longer than a half note (or rests: from one lead note's start to the next, `bass/melodySpace.js`), the bass walks in quarters under it into its next note (`instruments/bassFills.js`), on top of the walks above (never replacing them; the downbeat stays). The tune's note starts reach it as `tuneOnsets` through `bassPart`. Without a tune the line is unchanged. A first try that only walked where the tune was silent removed nearly all walking from Amazing Grace and was dropped.
- Gates and velocities shape articulation.
- Tuning constants sit at the top of the file.

## How the user thinks

- They change direction and add ideas often, and don't always have a clear vision up front. Make every design cheap to change: layers, plain data and seams, so a big change touches one place. Motto: make everything extendable. Build as if big code changes were expensive for a human.
- Code for a reader with about a year of full-stack experience: short, well-named functions with clear inputs and outputs, few comments (they dislike clutter; comment only where truly needed). Physics and DSP maths may be abstracted or come from a library.
- Build for one case first (e.g. bluegrass), leave seams for the next (Irish, custom patterns), and don't build UI for the others yet.

## Working with the user

The user listens to results in the browser and in Logic and gives feedback by ear. Keep musical tuning in named constants near the top of each module so it is easy to adjust.
